## 1. Что хотим

Сейчас игрок ставит любой модуль мгновенно и когда угодно, а экипаж только украшение. Хотим, чтобы экипаж стал частью игры:

1. Члены экипажа **дают задания** («поставь батареи»). До 10-го дня по 2 задания в день, дальше по 1.
2. Модуль строит **один свободный член экипажа**. Пока все заняты, строить нельзя.
3. Стройка идёт **1 минуту игрового времени** с анимацией.
4. Во время стройки может прийти **оповещение с портретом**: кто-то заболел. Выбор как при ЧП: «вылечить» (стоит воды и еды) или «проигнорировать».
5. Новый модуль **медпункт**.
6. Энергия, еда, вода и материалы показываются **в единицах, а не в процентах**.

## 2. Решения, которые уже подтверждены

| Вопрос | Решение |
|---|---|
| Можно ли строить то, о чём не просили? | Да. Задания это цели и подсказки, а не пропуск на стройку |
| Что такое «1 минута»? | 1 минута **игрового** времени. При дне в 25 с это 2,4 дня. Пауза останавливает стройку, ускорение ×2 ускоряет |
| Единицы | Реальные единицы с лимитом хранения. Максимум даёт Склад |
| Болезнь | Игнор: больной выбывает. Медпункт: лечит дешевле и быстрее |

## 3. Допущения, которые нужно подтвердить

Я выбрал их сам, пока вы были заняты. Любое можно поменять до начала кода.

1. **Порог 10-го дня.** Вы написали «9–11»: беру 10 одной константой `TASKS_BUSY_UNTIL`.
2. **Кислород и здоровье остаются в процентах.** Вы назвали энергию, еду, воду и материалы. Кислород в единицах не называли.
3. **Баланс не меняется.** 1 единица = 1 прежний процент, базовый лимит 100. Так все 17 сценариев проверки остаются валидными. Масштаб («420 л» вместо «42 л») меняется одной константой позже.
4. **Строителя выбирает игра**, а не игрок: свободный член экипажа, лучше с подходящей ролью. Игрок видит, кто строит.
5. **Последствия невыполненного задания:** падает настроение экипажа. На скорость стройки не влияет (лишнее усложнение, добавим, если команда захочет).
6. **Цена лечения:** 10 воды и 8 еды, с медпунктом вдвое меньше. Если проигнорировать: больной выбывает на 4 дня (с медпунктом на 2), здоровье экипажа −5. Если вылечили: отдыхает 1 день, с медпунктом сразу возвращается.
7. **Болезни не чаще одной за 5 дней, не больше 3 за миссию**, и только пока идёт стройка.

## 4. Подход

Выбран подход **«часы внутри движка»**. Рассмотрены три:

| Подход | Плюсы | Минусы |
|---|---|---|
| **А. Часы в движке (выбран).** Новое действие `tick(ms)`, движок сам считает время дня, стройку, болезнь | Всё детерминировано и проверяется роботом без браузера. Пауза и ×2 работают сами | `DayClock` перестаёт владеть временем, это правка чужого файла |
| Б. Стройка в целых днях (2 или 3 дня) | Движок не меняется | Нет плавной анимации и нет «ровно минуты» |
| В. Таймеры только в интерфейсе | Движок не трогаем | Состояние стройки вне `GameState`: не сохраняется, не проверяется роботом, расходится при паузе |

## 5. Модель данных

Все поля добавляются в `GameState` (`types.ts`) и сохраняются в localStorage.

```ts
type Role = "engineer" | "scientist" | "doctor" | "technician";

type CrewMember = {
  id: number;                       // 1..4, как в crewData.ts
  role: Role;
  morale: number;                   // 0..100
  status:
    | { kind: "free" }
    | { kind: "building"; slot: number }
    | { kind: "sick"; leftMs: number };
};

type PlacedModule = {
  slot: number; type: ModuleType; broken: boolean;
  build?: { leftMs: number; totalMs: number; crewId: number | null }; // есть, пока идёт стройка. crewId null: ждёт свободного
};

type Task = {
  id: string;                       // "battery", "stock-water" ...
  giver: number;                    // id члена экипажа
  issuedDay: number; deadline: number;
  status: "open" | "done" | "missed";
};

// в GameState добавляются:
crew: CrewMember[];
tasks: Task[];
clockMs: number;                    // сколько мс прошло в текущем дне
seed: number;                       // для детерминированных случайностей (болезни)
illness: { crewId: number; slot: number } | null;
```

Модуль в стройке **не работает** и не потребляет, но занимает клетку. Стоимость списывается при старте.

## 6. Поведение движка

**Действия:**
- `tick(ms)`: двигает `clockMs` и таймеры стройки и болезни. Когда `clockMs >= DAY_MS`, сам вызывает `nextDay` и переносит остаток. `DAY_MS = 25000` переезжает в движок.
- `nextDay`: кнопка «Следующий день» отправляет `tick(DAY_MS - clockMs)`, чтобы стройка шла вместе со временем.
- `build`: если нет свободного члена экипажа, отказ. Иначе берём свободного (сначала с подходящей ролью), списываем стоимость, ставим стройку на `BUILD_MS = 60000`.
- `resolveEvent`: работает и для болезни (см. ниже).

**Стройка:** `tick` уменьшает `leftMs`. На 0 модуль начинает работать, строитель становится свободным, задание на этот модуль закрывается. Если строитель заболел и не вылечен, стройка встаёт (`crewId: null`) и сама подхватывается первым свободным.

**Задания (генерируются из состояния, без ручного расписания):**
- Каждый день `nextDay` выдаёт новые задания: `TASKS_PER_DAY` = 2 до дня `TASKS_BUSY_UNTIL`, потом 1.
- Кандидаты идут по приоритету: чего базе не хватает (первый жилой модуль, панели, воздух, лёд, теплица, убежище к вспышке, батарея к ночи, медпункт, склад), плюс задания вида «держи воды не меньше N».
- Задание уже выполнено, если условие верно, поэтому его не выдают.
- Даёт задание тот, чья роль подходит: инженер за энергию, учёный за лёд и камни, врач за медпункт, техник за жизнеобеспечение.
- Срок обычно 4 дня, у убежища (вспышка) и батареи (ночь) жёсткий.
- Сделано в срок: настроение +10. Просрочено: −10.
- Заменяет статичный список из PR #3 (`engine/tasks.ts`). Его условия «сделано» (есть ли модуль) переиспользуются как проверка выполнения.

**Болезнь:**
- При старте стройки движок бросает кубик по `seed`: заболеет ли строитель, и на какой доле стройки. Это даёт «болезнь во время стройки», но результат воспроизводим в проверках.
- Новое событие `illness` в `events.json` с выборами `treat` и `ignore`. Цены читаются из данных, как сейчас у вспышки и поломки. Для скидки от медпункта нужно новое поле `costWith: { module, cost }` рядом с существующим `costWithout`.
- `treat`: платим воду и еду, больной отдыхает короткое время.
- `ignore`: больной выбывает на дольше, его стройка встаёт, здоровье экипажа −5.

**Медпункт:** новый `ModuleType` `medbay`. Цена в энергии и материалах, небольшой расход энергии. Эффект только сокращает лечение и сроки болезни (раздел 3, пункт 6).

**Единицы и лимиты:**
- Новый `capacity(state)`: база 100 на ресурс. Склад даёт +100 воды, еды и материалов. Батарея даёт +50 энергии.
- `clamp` режет по лимиту, а не по 100. Кислород и здоровье остаются 0–100.
- Единицы: вода в литрах, еда в кг, энергия в кВт·ч, материалы в кг. Названия в словарях i18n (`unit.*`).
- Новый модуль `storage` (Склад). На макете он уже есть.

## 10. Порядок и риски

**Порядок (каждый шаг сливается отдельно, проверки остаются зелёными):**
1. Единицы, лимиты и склад. Без изменения баланса.
2. Экипаж, часы в движке, стройка с таймером.
3. Генератор заданий и их интерфейс.
4. Болезнь и медпункт.
5. Разбор, тексты, проверки.

**Риски:**
- **Конфликты.** Открыты PR #1 (материалы) и #3 (лёд, камни, список заданий). Они правят `types.ts` и `engine.ts`, как и мы. Начинать надо **после их слияния в main**, иначе будем снова решать конфликты.
- **Чужой файл.** Часы переезжают из `ui/DayClock.tsx` (@w1lderrr) в движок. Нужно его согласие. Интерфейс `DayClock` останется тем же, поменяется только то, что он отправляет `tick`.
- **Пропускная способность.** 4 человека по 2,4 дня на стройку это около 1,7 стройки в день. Если все задания будут «построй X», до 10-го дня их 20, а успеть можно меньше. Поэтому часть заданий не стройки («держи воды не меньше N», «добудь материалы»), а сроки в 4 дня. Это нужно проверить игрой.
- **Миссия 20 дней.** Одна стройка занимает 12% миссии. Если команда хочет миссию в 30 дней, цифры сдвигаются.
